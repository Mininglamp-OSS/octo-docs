Most problems surface at deploy time and fall into two buckets: the **platform** isn't fully up,
or it's up but **auth / storage** is wired wrong. The [smoke test](/guides/operators/deploy-compose)
(`sudo ./setup.sh --smoke-test`) tells you which — it groups its 11 probes into `[infra]` and
`[user-path]` failure domains.

## Startup

<AccordionGroup>
  <Accordion title="docker compose up complains about port collisions">
    Another process holds one of Octo's ports. The only port that must be free for clients is
    `28080` (`OCTO_HTTP_PORT`); the rest default to loopback. Change the offending
    `OCTO_*_PORT` in `docker/.env`, or stop the conflicting process.
  </Accordion>
  <Accordion title="A service never becomes (healthy)">
    `--up` blocks until every service is healthy, then prints `docker compose ps` and names the
    failing ones. Inspect logs: `cd docker && docker compose logs --tail 200 <service>`. A cold
    MySQL init can take 60–90 s on first boot — give it time before assuming failure.
  </Accordion>
  <Accordion title="setup.sh --up exits: docker/.env missing">
    `--up` is start-only and never regenerates secrets. Run `./setup.sh` first to create
    `docker/.env`, then `sudo ./setup.sh --up`. (Only `--up --force` will bootstrap fresh
    secrets — never use it on a stack whose `.env` is already in production.)
  </Accordion>
  <Accordion title="Permission denied reading docker/.env">
    `.env` stays `root:600` because it holds every high-value secret. Run `--up` and
    `--smoke-test` with `sudo`.
  </Accordion>
</AccordionGroup>

## The `[infra]` domain failed

A container is down, nginx isn't reverse-proxying, or a host port is firewalled. Start with
`docker compose ps` and `docker compose logs`. Confirm the health endpoints respond:
`/_nginx_up`, `/api/v1/health`, `/` (see [Scale and observe](/guides/operators/scale-and-observe)).

## The `[user-path]` domain failed

The platform is up but the contract is wrong — auth wired incorrectly, MinIO IAM creds desynced,
or SigV4 signing mismatched. Look at `octo-server` **and** MinIO together, not at nginx.

<AccordionGroup>
  <Accordion title="Admin login fails">
    Open the configured HTTPS console and use the **current** password for the intended platform-manager account. The account seeded by the server is named `superAdmin`; other manager accounts use their own usernames. Follow the [admin console sign-in guidance](/guides/teams/admin-console#sign-in-and-understand-the-boundary), including any required email MFA.

    The password printed by `setup.sh` or stored as `OCTO_ADMIN_PWD` in `docker/.env` is **bootstrap-only**, not a recovery credential. [Compose passes it to the server](https://github.com/Mininglamp-OSS/octo-deployment/blob/afd3747b8d952b3e4fab2fad063d7afdd0cb0756/docker/docker-compose.yaml#L711-L717), whose [account initializer](https://github.com/Mininglamp-OSS/octo-server/blob/adb7c385386c558d78be8b6fbf7881392fab4475/modules/user/api_manager.go#L2107-L2162) returns when the configured account already exists. After a password change, the saved bootstrap value can be stale. Changing that value or restarting the server does not reset an existing account.

    If an authorized operator still has a valid **superAdmin-role session**, the released [password-reset endpoint](https://github.com/Mininglamp-OSS/octo-server/blob/adb7c385386c558d78be8b6fbf7881392fab4475/modules/user/api_manager.go#L758-L812) is `POST /v1/manager/user/resetpassword`. Confirm the target account's `uid`, then submit `new_password` and matching `new_password_confirmation` through the protected API entry point using that session. The server requires the superAdmin role and a password that satisfies its strength policy. This is an authenticated administrative operation, not a way to recover a lost session or bypass MFA.

    After a successful reset, sign in with the new password and complete any required MFA. If the request fails or times out, have the operator check the account and session state before retrying: the [password update can commit before session revocation or device logout fails](https://github.com/Mininglamp-OSS/octo-server/blob/adb7c385386c558d78be8b6fbf7881392fab4475/modules/user/session_revocation.go#L124-L174). An error does not prove that the old password is still valid.

    If no valid superAdmin session is available, the checked Server v1.24.0 [manager routes](https://github.com/Mininglamp-OSS/octo-server/blob/adb7c385386c558d78be8b6fbf7881392fab4475/modules/user/api_manager.go#L106-L128) provide no unauthenticated password-reset endpoint. Ask the deployment owner to arrange recovery for the deployed version. This guide does not provide a verified offline database-recovery procedure. Do not rerun setup with `--force`, delete the account, or remove data as a password-reset shortcut. Source checks do not establish that a recovery procedure has been tested in your deployment.
  </Accordion>
  <Accordion title="File upload / presigned PUT returns 403 SignatureDoesNotMatch">
    A browser-direct upload must echo the `contentType` (and `contentDisposition` if set) returned
    by the credentials endpoint as the matching PUT headers — they're covered by the SigV4
    signature. Also ensure the object-storage bucket allows PUT from the `octo-web` origin (CORS).
  </Accordion>
  <Accordion title="WebSocket / real-time not working">
    Browser chat flows through nginx `/ws`. Make sure your reverse proxy forwards the WebSocket
    upgrade. Native chat transports (`25100`/`25200`) are only needed for native clients connecting
    directly to WuKongIM.
  </Accordion>
</AccordionGroup>

## Auth & credentials

Every "token bad" reason collapses to a single `AUTH_INVALID_CREDENTIAL` (401) — by design, to
prevent enumeration. The real reason is in the server's audit log only; don't branch on a
sub-reason. See [Security & auth](/concepts/security-and-auth) and the
[error reference](/reference/errors-and-envelopes).

<Warning>
  **Redis runs with no auth by default** and is bound to loopback. If a client can't reach it,
  check the bind — but never widen `OCTO_REDIS_BIND` without also setting a password. See
  [Security hardening](/guides/operators/security-hardening).
</Warning>
