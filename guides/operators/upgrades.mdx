## Runtime v1.1.3 compatibility

This guide targets the published [Octo Runtime v1.1.3](https://github.com/Mininglamp-OSS/octo-runtime/releases/tag/v1.1.3),
verified at [`fe19d3504315`](https://github.com/Mininglamp-OSS/octo-runtime/blob/fe19d350431534da4ed3a76f3466add4ced86d81/README.md). It requires **Node.js 24.x or 26.x** and an installed,
authenticated Provider. Runtime does not install Provider software or sign in for you.
`octo-runtime` manages local execution; [`octo-cli`](/guides/bot-developers/drive-octo-with-cli)
is the separate business API client.

<Warning>
  The legacy `octo-daemon upgrade` / pm2 instructions do not migrate to this architecture.
  For an old daemon or Runtime 1.0.1 installation, first stop and remove its old services using
  that version's commands or service manager. Then uninstall the old npm package and install
  `@mininglamp-oss/octo-runtime@1.1.3`, and configure it again. Uninstalling an npm package alone
  does not stop old processes or remove service definitions. There is no automatic migration
  of old configuration, state, or service definitions. Follow the
  [release-specific reinstallation instructions](https://github.com/Mininglamp-OSS/octo-runtime/blob/fe19d350431534da4ed3a76f3466add4ced86d81/DEPLOYMENTS.md#旧版弃用与重新安装).
</Warning>

For a fresh installation:

```bash
npm install -g @mininglamp-oss/octo-runtime@1.1.3
octo-runtime --help
```

## Configure before starting

The Executor Kernel and each Extra are independent components. Channel Gateway connects
Octo IM Bots to the Kernel; WebUI and WeCom are separate Extras. Configure the full Gateway
declaration with `octo-runtime extraset channel-gateway < gateway.json` using the
[released Gateway configuration guide](https://github.com/Mininglamp-OSS/octo-runtime/blob/fe19d350431534da4ed3a76f3466add4ced86d81/packages/octo-runtime-extra-channel-gateway/README.md).
`extraset` replaces the whole declaration, including every Bot you want to retain. It does
not connect Bots, install services, or restart running components.

Runtime Home defaults to `~/.octo-runtime` on macOS/Linux and `%LOCALAPPDATA%\OctoRuntime`
on Windows, with a home-directory fallback. Use the same explicit `--home PATH` on every
command when you choose another Home. The CLI stores the Gateway declaration, including
configured Bot credentials, locally; its POSIX configuration file mode is `0600`.
Protect these files and backups. `extraget` prints the full saved declaration, including
credentials; do not paste its output into tickets or logs.

Review permission settings before connecting Bots. Gateway defaults `approval_mode` to
`full_access`; supported modes and their effect depend on the selected Adapter. Local
execution approval does not grant Octo resource permissions. See the
[release-specific permission and sender settings](https://github.com/Mininglamp-OSS/octo-runtime/blob/fe19d350431534da4ed3a76f3466add4ced86d81/packages/octo-runtime-extra-channel-gateway/README.md#插件字段).

## OpenClaw approval compatibility

The Runtime OpenClaw Adapter selects its contract from each actual Gateway handshake:
`server.version`, protocol, methods, and events. An unknown version or missing required
capability fails before session creation. Its 27 audited release contracts do not represent
27 deployments tested with real models, reviewers, and IM delivery. This is separate from
the `openclaw-channel-octo` channel plugin.

<Warning>
  Requesting `ask` does not always retain human approval. Legacy contracts cannot confirm a
  human reviewer. Modern contracts fall back when the approval methods/events are unavailable,
  or when advertised scopes include neither `operator.approvals` nor `operator.admin`.
  The Adapter then selects `full_access` and emits a `run.notice` with
  `category: permission_fallback`; the approval bridge automatically answers `allow-once`,
  without waiting for human approval. For modern contracts that advertise scopes, effective
  full access requires `operator.admin`; without it, execution fails with
  `OPENCLAW_PERMISSION_UNAVAILABLE`, including when a fallback would require full access.
  `assisted` is unsupported. Review the target Gateway before relying on `ask`.
</Warning>

See the released [handshake and permission selection](https://github.com/Mininglamp-OSS/octo-runtime/blob/fe19d350431534da4ed3a76f3466add4ced86d81/packages/octo-runtime-adapter-openclaw/src/compatibility.ts),
[execution notice](https://github.com/Mininglamp-OSS/octo-runtime/blob/fe19d350431534da4ed3a76f3466add4ced86d81/packages/octo-runtime-adapter-openclaw/src/index.ts), and
[automatic approval bridge](https://github.com/Mininglamp-OSS/octo-runtime/blob/fe19d350431534da4ed3a76f3466add4ced86d81/packages/octo-runtime-adapter-sdk/src/approval.ts).
Gateway sender admission is a separate setting; review
[the sender and group rules](/concepts/the-agent-model#gateway-message-admission).

## Custom Extra migration in v1.1.3

The CLI merges its built-in `manifest.json` with `<Runtime Home>/manifest.json`.
The manifest declares Adapter and Extra modules; each Extra's saved configuration still owns
`enabled` and business settings. A custom Extra must appear in the effective manifest's
`extras` array before it can run. Relative module paths resolve from the manifest that declared
them, not the current working directory. Built-in names take precedence over Home extensions.

Old Extra configurations may keep `module` only if its text exactly matches the effective
manifest declaration. For manifest-relative module paths, omit the legacy field: the saved
Extra configuration does not accept a relative `module` value such as `./plugins/example.mjs`.
Alternatively, explicitly save a complete configuration without that
legacy field using `extraset`. Keep all Bot/configuration entries you intend to retain.
`EXTRA_MANIFEST_DECLARATION_REQUIRED` indicates a missing declaration;
`EXTRA_MODULE_MIGRATION_REQUIRED` indicates conflicting module text. Existing files,
identities and credentials are not rewritten automatically.

`--manifest PATH` replaces the whole built-in/Home selection rather than adding to it;
a legacy Adapter-only override has no Extra entries. Modules are loaded only for the selected,
enabled service, and are not automatically installed or hot-reloaded. Review the
[release-specific loading and migration contract](https://github.com/Mininglamp-OSS/octo-runtime/blob/fe19d350431534da4ed3a76f3466add4ced86d81/docs/en/concepts/module-loading.md)
before restarting custom Extras. These CLI manifests do not configure SDK hosts.

## Start and manage independent services

<Warning>
  **Linux systemd limitation in v1.1.3:** the released renderer quotes `WorkingDirectory`
  and `append:` log paths as command arguments. systemd can reject the working directory
  and ignore log destinations, preventing a usable service. The fix in
  [Runtime #114](https://github.com/Mininglamp-OSS/octo-runtime/pull/114) was merged after this
  release. Repeating `install` with v1.1.3 generates the same defective directives; it does
  not apply that fix. Wait for a release containing the fix before relying on Linux user
  service installation. Foreground `run` avoids service registration; keep the Kernel and
  each Extra in separate foreground sessions. See the
  [released renderer](https://github.com/Mininglamp-OSS/octo-runtime/blob/fe19d350431534da4ed3a76f3466add4ced86d81/packages/octo-runtime-cross-service/src/systemd.ts).
</Warning>

For **Linux v1.1.3**, use separate foreground sessions. Keep the Kernel session running:

```bash
octo-runtime executor-kernel run
```

In another session, keep the Gateway running:

```bash
octo-runtime channel-gateway run
```

For **macOS and Windows**, start the native user services:

```bash
octo-runtime executor-kernel start
octo-runtime channel-gateway start
```

On either path, check status from a separate session:

```bash
octo-runtime status --json
```

<Warning>
  `start` installs a missing component's user service and enables its autostart before
  starting it. Plain `install`, including a repeated install, also enables autostart.
  These commands change service registration; they are not read-only readiness checks.
</Warning>

| Action | Effect in v1.1.3 |
|---|---|
| `install` | Register this component and enable autostart; does not itself prove readiness. |
| `install --autostart=false` | Register or update this component with autostart disabled. |
| `start` | Install if missing, then start and wait for local readiness; preserve settings of an existing service. |
| `restart` | Restart an installed, enabled component; does not install a missing one. |
| `stop` | Stop this component while retaining its autostart setting. |
| `uninstall` | Stop and remove this component's service; retain user data and credentials. |
| `run` | Run this component in the foreground without registering a user service. |

An explicitly disabled service returns `SERVICE_DISABLED` on start; use
`install --autostart=true` to enable it again. For foreground execution without service
autostart, use the component's `run` command. Stopping or removing one Extra does not stop
the Kernel or other Extras. Either service may start first; an Extra can report
`kernel_available=false` until the Kernel is available.

Native services use macOS LaunchAgent, Linux systemd user services, or Windows current-user
Task Scheduler. Autostart happens at user sign-in or user-manager activation; it does not
promise unattended operation before login. Service/IPC readiness, Provider authentication,
and Bot connectivity are separate states. `status --json` is needed for scripts that parse
JSON; the default output is readable text.

## Upgrade an existing v1.1 installation

Choose a published version and review its migration requirements. Schedule changes when
there are no active tasks, stop the affected components, update the pinned npm package,
then start them again using the same Home. If the Node executable or installation path
changes, run the affected component's `install` again to update its service definition and
review autostart, subject to the Linux v1.1.3 limitation above. A Kernel restart does not resume or re-invoke old runs. After Gateway
configuration changes, restart that Gateway component.

These contracts were checked against the released
[CLI implementation](https://github.com/Mininglamp-OSS/octo-runtime/blob/fe19d350431534da4ed3a76f3466add4ced86d81/apps/cli/src/main.ts) and
[CLI usage guide](https://github.com/Mininglamp-OSS/octo-runtime/blob/fe19d350431534da4ed3a76f3466add4ced86d81/CLI_USAGE_GUIDE.md). Package installation, service registration,
local readiness, and successful Provider/IM operation are distinct checks.

## Upgrading the platform itself

For the server and clients, pin `mininglamposs/octo-*` images to a release tag (never `:latest`),
pull the new tags, and roll:

```bash
docker compose up -d       # Compose
# or
helm upgrade octo ...      # Kubernetes
```

<Info>
  Review [Backup and restore](/guides/operators/backup-and-restore) before a major upgrade.
  When maintaining generated references, use the matching released source contract rather
  than assuming an upstream `main` change has shipped.
</Info>
