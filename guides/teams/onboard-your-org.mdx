Once your [stack is deployed](/get-started/quickstart-deploy), the first job is to get your
organization and people in. Octo is multi-tenant and space-scoped, so onboarding is about
creating a space, inviting members with the right roles, and opening the channels they'll work
in.

## Prerequisites

- A running Octo instance with a platform-manager account configured for your deployment.
- An HTTPS ingress with a valid certificate for the [admin console](/guides/teams/admin-console), for example `https://octo.example.com/admin/`. Replace this hostname with your configured ingress. Changing the URL to `https://` does not enable TLS in Compose.

<Warning>
  Before anyone signs in from another machine, require HTTPS for the console, web client, and their browser-facing APIs. Never send passwords, MFA codes, or session tokens over plaintext HTTP across the network. A private network or VPN is an additional access control, not a replacement for HTTPS. Protect administrative API entry points as well as `/admin/`, and prevent direct access to plaintext listeners that bypass the ingress. Follow the [admin console access guidance](/guides/teams/admin-console#access) for API routing and proxy-to-backend protection.
</Warning>

For local evaluation only, you can use `http://127.0.0.1:28080/admin/` on the machine running the stack after restricting its HTTP listener to local access. A loopback URL does not change the bind address or firewall rules; it must not leave the plaintext port reachable from other machines.

## Steps

<Steps>
  <Step title="Create the organization (space)">
    In the admin console, create a **space** — the tenant boundary that owns all channels, users,
    and data. Everything below is scoped to it.
  </Step>
  <Step title="Invite members with roles">
    Invite people by email. Each member carries a **role** within the space:

    | Role | Value | Can |
    |---|---|---|
    | Member | `0` | Participate in channels they belong to |
    | Admin | `1` | Manage members, channels, and moderation |
    | Owner | `2` | Everything, including space-level settings |

    You can update a member's role later — invites themselves carry an owner-vs-member/admin
    distinction.

    <Note>
      Members sign in to the **web client** through its configured HTTPS ingress, for example `https://octo.example.com/` when it shares the console's host. Local evaluation on the stack's machine may use `http://127.0.0.1:28080/` only under the listener restrictions above. See [Clients](/guides/teams/clients) for the desktop, mobile, and browser-extension options.
    </Note>
  </Step>
  <Step title="Set up channels">
    Create the group and topic channels your team needs. Access is governed per channel by ACL on
    top of the space role — see the [Security & auth model](/concepts/security-and-auth).
  </Step>
  <Step title="Add an AI agent (optional)">
    Bring an agent into the workspace so agents are first-class from day one — follow
    [Connect your first AI bot](/get-started/quickstart-connect-a-bot).
  </Step>
</Steps>

<Info>
  The console is a front-end for `octo-server` administration. Its primary manager APIs use `/v1/manager/*`; `/admin/` is the browser UI path. Server authentication and role checks enforce administrative access; a visible or hidden button does not grant or revoke server permissions. See the [admin console guide](/guides/teams/admin-console) for the fixed release sources, sign-in flow, and API protection requirements. Verify these controls in your deployment before onboarding members.
</Info>
