### OCTO_USER_API_KEY_SECRET

用户密钥别名 / 密钥管理器与加固后的用户 API 密钥（`uk_`）需要此变量。没有默认值。为每个 `octo-server` 进程注入这个准确名称的环境变量；代码直接读取它，不读取 YAML 配置项或 `TS_` 覆盖项。

必须恰好是**环境字符串的 32 个字节**，直接使用原值。服务端不会做 hex 解码、Base64 解码或去除空白。使用 32 个 ASCII 字符以避免多字节文本带来的歧义，不要包含换行。

仅在首次配置此主密钥、并确认没有已有密文或用户 API 密钥依赖旧值时，在安全的密钥配置流程中使用下方命令生成。它输出 32 个 ASCII 十六进制字符，即 32 个原始字节。按文本原样保存，不要解码。`openssl rand -hex 32` 会输出 64 个字符，不符合此变量要求。

```bash
openssl rand -hex 16
```

将值保存在部署密钥存储中，限制访问，并随数据库恢复材料安全备份。所有服务端副本、重启、升级及恢复必须使用相同的值。它与 `OCTO_MASTER_KEY` / `DMWORK_MASTER_KEY` 不同；设置后两者不会自动提供此变量。

<Warning>
  不要在日常部署时重新生成此值。修改或丢失它会导致已有密钥别名及用户 API 密钥的密文无法解密，也会改变加固后的用户 API 密钥查询所依赖的 HMAC 校验值。当前没有内建多密钥轮换。轮换需要规划密文和 API 密钥校验值迁移（或重新签发）；不能只替换环境变量。
</Warning>

缺失或长度错误不会阻止服务端启动。usersecret 模块会在启动时记录包含 `OCTO_USER_API_KEY_SECRET must be exactly 32 bytes` 的错误；密钥管理 CRUD 与 bot resolve 接口返回 HTTP 500（`err.server.usersecret.resolve_failed`）。依赖此值的用户 API 密钥操作也会失败。修正注入的环境变量后，重新创建或重启全部服务端进程；容器健康并不代表此功能正常。

部署说明: [Docker Compose](/zh/guides/operators/deploy-compose), [Kubernetes](/zh/guides/operators/deploy-kubernetes).
