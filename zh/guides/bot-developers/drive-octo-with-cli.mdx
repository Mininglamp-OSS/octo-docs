**[`octo-cli`](https://github.com/Mininglamp-OSS/octo-cli)** 是一个单一二进制的 REST 客户端，
专为 **AI 智能体通过 `exec` 调用** 而设计。如果说[频道](/zh/guides/bot-developers/choose-a-channel)
让智能体能够*回复*，那么 `octo-cli` 就让它能够*行动*——发送消息、列出群组、管理话题、
上传文件。智能体调用会在 stdout 上输出结构化的 JSON 信封（envelope），以非交互方式运行；
凭据配置另由操作人员完成。

## 安装

```bash
npm install -g @mininglamp-oss/octo-cli@0.18.0
# or
go install github.com/Mininglamp-OSS/octo-cli/cmd/octo-cli@v0.18.0
```

两种安装方式均固定为下文的 v0.18.0 契约；npm 包会解析出匹配的预构建平台二进制。
其他 tag 或 `latest` 的 URL 选择规则可能不同。

## 认证

本节核实于已发布的 [CLI v0.18.0](https://github.com/Mininglamp-OSS/octo-cli/releases/tag/v0.18.0)，
源码版本为 [`d564a63bbd8e`](https://github.com/Mininglamp-OSS/octo-cli/blob/d564a63bbd8ec2dd4305a40a64fe0179ca9c667f/internal/cmdutil/factory.go)。先用 `octo-cli version` 确认本机版本。

普通凭据模式（未设置 `OCTO_CREDENTIAL_MODE`）先尝试已保存的 profile，再尝试环境凭据。
创建 profile 时，由操作人员运行以下配置命令，在隐藏提示中输入 token，不要把 token 放进命令参数：

```bash
octo-cli auth login --profile staging-bot --api-base-url "https://octo-staging.example.com"
```

将示例 URL 替换为该凭据对应的可信网关 origin，不带 API 路径。
此命令只保存本地凭据与元数据，不验证远端认证是否通过。
`auth login` 是操作人员的配置步骤，与智能体执行的非交互命令分开。

<Warning>
  没有选择器时，即使设置了 `OCTO_BOT_TOKEN`，唯一的已保存 profile 仍会被选中；
  多个 profile 会报歧义错误，不会回落到该 token。只有存储中没有 profile 时才回落到环境凭据。
  环境 provider 先检查 `OCTO_TOKEN`，再检查 `OCTO_BOT_TOKEN`。

  v0.18.0 中，继承的非空 `OCTO_API_BASE_URL` 优先于所选 profile 保存的 URL。
  因此，`--profile` 可以选中一个 Bot 的凭据，请求却仍发往另一个网关。
  切换 profile 不会撤销先前的全局 `export`。`auth status` 展示保存的 profile 元数据，
  其中的 URL 不能证明实际请求目标。执行业务命令前，先确认凭据与可信网关匹配。
</Warning>

`--profile` 与显式 `--bot-id` 用于选择已保存的 profile；找不到或匹配冲突都会失败。
`OCTO_BOT_ID` 也可选择已保存的 profile；存储为空且未显式指定 profile 时，
该环境 ID 可标识环境凭据，存储非空却匹配不到则失败。
`OCTO_CREDENTIAL_MODE=task` 不走上述普通凭据链，而是单独使用 daemon 注入的 Loop 任务凭据，
拒绝 profile/Bot 选择器及非 Loop 命令。不要为使用本 Bot 指南而改掉 daemon 的任务模式标记。

### 检查本地请求配置

显式选择 profile，并将 URL 限定在当前命令。这项预检不发送 HTTP：

```bash
OCTO_API_BASE_URL="https://octo-staging.example.com" \
  octo-cli --profile staging-bot --format json config show
```

配置有效时，核对 `data.api_base_url`、`data.profile`、`data.bot_token_source` 与 `identity`
是否符合预期网关及 Bot。本例应显示可信的 staging 地址、profile `staging-bot`，
以及来源 `profile:staging-bot`。遇到配置错误或身份字段不符时，先排查，不要继续执行。
部分非结构化配置错误会使 `config show` 回落到环境值；仅退出成功不代表所选 profile、
身份、网关可信性或远端权限已经验证。`config show` 和 `auth status` 都不测试远端授权。

每条业务命令都重复使用相同 URL 与 profile：

```bash
OCTO_API_BASE_URL="https://octo-staging.example.com" \
  octo-cli --profile staging-bot group list
```

只有该 profile **已经保存正确的网关 URL** 时，移除继承的 URL 后才能依赖它。
如果 profile 的 URL 为空，v0.18.0 会回退到生产默认地址 `https://im.deepminer.com.cn`。
仅清除环境变量并不能安全地选中 staging；任何变更后都应重新核对解析结果。

### 不使用 profile 的环境凭据预检

普通 Bot 进程可由密钥管理器注入 `OCTO_BOT_TOKEN`。使用独立、有效且没有已保存 profile 的
`OCTO_CONFIG_DIR`，省略 profile/Bot 标志，并为当前命令清空竞争的 `OCTO_TOKEN` 和 `OCTO_BOT_ID`。
替换以下目录和可信网关地址：

```bash
OCTO_CONFIG_DIR="/path/to/dedicated-empty-octo-config" \
  OCTO_TOKEN="" OCTO_BOT_ID="" OCTO_API_BASE_URL="https://octo-staging.example.com" \
  octo-cli --format json config show
```

预期 `data.profile: null`、`data.bot_token_source: "env:OCTO_BOT_TOKEN"`、一致的
`identity.source` 及目标 `data.api_base_url`。仅退出成功，或配置错误后显示环境来源，均不足以继续：
应先排除错误并确认该存储有效且为空。此预检不验证 token 在远端对应的 Bot 身份或权限。
后续命令保持相同目录、环境与 URL；采用 profile 的进程则应保留上文的显式 profile。

发行版分别实现了[凭据选择](https://github.com/Mininglamp-OSS/octo-cli/blob/d564a63bbd8ec2dd4305a40a64fe0179ca9c667f/internal/credential/file_provider.go)、
[环境回落](https://github.com/Mininglamp-OSS/octo-cli/blob/d564a63bbd8ec2dd4305a40a64fe0179ca9c667f/internal/credential/env_provider.go)、
[URL 选择](https://github.com/Mininglamp-OSS/octo-cli/blob/d564a63bbd8ec2dd4305a40a64fe0179ca9c667f/internal/cmdutil/factory.go)、
[保存的认证元数据](https://github.com/Mininglamp-OSS/octo-cli/blob/d564a63bbd8ec2dd4305a40a64fe0179ca9c667f/cmd/auth.go)、
[配置诊断](https://github.com/Mininglamp-OSS/octo-cli/blob/d564a63bbd8ec2dd4305a40a64fe0179ca9c667f/cmd/config.go)与
[请求目标及 Bearer 凭据](https://github.com/Mininglamp-OSS/octo-cli/blob/d564a63bbd8ec2dd4305a40a64fe0179ca9c667f/internal/client/client.go)。

可选：`OCTO_SPACE_ID`（面向平台级助理的空间上下文）、`OCTO_FORMAT`
（`json` | `table` | `csv` | `ndjson`）。

## 使用它

以下示例逐条使用已核对的 profile 与网关组合：

```bash
OCTO_API_BASE_URL="https://octo-staging.example.com" \
  octo-cli --profile staging-bot group list
OCTO_API_BASE_URL="https://octo-staging.example.com" \
  octo-cli --profile staging-bot message send --data '{"channel_id":"chat-1","channel_type":1,"payload":{"text":"hi"}}'
OCTO_API_BASE_URL="https://octo-staging.example.com" \
  octo-cli --profile staging-bot thread create group-no-example --name "design review"
OCTO_API_BASE_URL="https://octo-staging.example.com" \
  octo-cli --profile staging-bot file upload --file ./report.pdf
OCTO_API_BASE_URL="https://octo-staging.example.com" \
  octo-cli --profile staging-bot docs list --sort updatedAt:desc
OCTO_API_BASE_URL="https://octo-staging.example.com" \
  octo-cli --profile staging-bot file download abc123 --jq '.data.url'
```

将 `group-no-example` 替换为你的群组编号；`thread create` 使用位置参数接收它。CLI 标志名可能与 JSON 字段名不同，例如 `--channel-id` 对应 `channel_id`。话题创建、消息发送与文件上传三种参数形式以 [octo-cli v0.18.0](https://github.com/Mininglamp-OSS/octo-cli/releases/tag/v0.18.0) 为准。添加 `--dry-run` 可以在发送前预览请求。

整个命令树——**覆盖所有域的每一个 REST 操作**——是从内嵌在二进制中的 OpenAPI 规范
自动注册的，因此它与服务器保持步调一致。每个命令都与一个 REST 操作 1:1 对应。

<Info>
  用 `--data '<json>'` 传入请求体，用 `--jq '<expr>'` 对 JSON 信封做后处理。
  错误输出到 stderr，并带有确定性的分类体系——非常适合在智能体循环中编写脚本。
</Info>

## 将其接入智能体

给智能体授予 `exec octo-cli` 的权限（例如，一个 Claude Code 助理的 `allowedTools`，
或 Claw 运行时的 Agent Skills）。随后智能体便调用 `octo-cli` 命令来直接操作 Octo——
这正是 [Claw 频道](/zh/guides/bot-developers/openclaw-and-claw-channels)实现其“手”的方式。
